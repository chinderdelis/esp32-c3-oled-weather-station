<p class="wp-block-paragraph">But finding the original reference source for them is proving difficult, but I think I&#8217;ve managed to piece together the basics from various sources for what I need to get them working.  So, I thought it would be worth making a few notes.</p>



<p class="wp-block-paragraph">They appear to be &#8220;ABRobot ESP32-C3 0.42 OLED&#8221; devices, at least when first powered on they display the text &#8220;ABrobot&#8221;. But I don&#8217;t seem to be able to access the ABRobot website myself and it is all in (one presumes) Chinese.  It is a small, 20x25mm board with 2.54mm pitch pins.</p>



<p class="wp-block-paragraph">The original purchase site has the following descriptions:</p>



<p class="wp-block-paragraph"><em>&#8220;ESP32 C3 OLED development board is based on ESP32C3FN4/FH4, which is designed and produced core boards.&nbsp;It has a built-in 4M Flash. It has two modes: WiFi and Bluetooth, with a ceramic antenna,&nbsp;equipped with a 0.42 -inch OLED screen, and supports USB download.&#8221;</em></p>



<ul class="wp-block-list">
<li><em>Voltage: 3.3~6V</em></li>



<li><em>WiFi: 802.11b/g/n protocol, 2.4GHz</em></li>



<li><em>Bluetooth: BT 5.0</em></li>



<li><em>SPI Flash: Built in 4M</em></li>



<li><em>Pin interfaces: 1xI2C, 1xSPI, 2xUART, 11xGPIO (PWM), 4xADC</em></li>



<li><em>Onboard LED blue light: GPO8 pin</em></li>



<li><em>BO0: Download button, long press BO0 button and plug in the USB cable, then release your hand to enter &#8220;download mode&#8221;</em></li>



<li><em>RST: Reset button, program running restarts or resets.</em></li>



<li><em>USB interface: can be used as a power supply for circuit boards or as a communication interface for connecting PCs and ESP32C3.</em></li>



<li><em>Size: 24.8mm * 20.45mm</em></li>
</ul>



<p class="wp-block-paragraph">But also the curious statement:</p>



<p class="wp-block-paragraph"><em>&#8220;This screen is different from Other 0.42 -inch screen. The starting point of the screen is 12864 (13, 14).  Please pay attention before buying, you must not directly replace other 0.42 -inch screens.&#8221;</em></p>



<p class="wp-block-paragraph">There is an additional review comment that seems to give some more information:</p>



<p class="wp-block-paragraph"><em>&#8220;The ABROBOT development board with ESP32-C3 is a compact IoT platform with native USB CDC support, eliminating the need for an external converter. To ensure proper functionality, it requires flashing a new bootloader. The onboard OLED display has an effective resolution of 72&#215;40 pixels, though libraries like U8g2 require setting the resolution to 128&#215;64. The display is connected via I2C using GPIO5 (SDA) and GPIO6 (SCL) with an address of 0x3C. A display offset of (30, 12) ensures proper rendering, and drawing is limited to 72&#215;40 pixels to avoid clipping. Other features include a built-in LED on GPIO8, UART communication on GPIO21 and GPIO20, a second I2C on GPIO8 and GPIO9, SPI, ADC (GPIO0 to GPIO5), and the BOOT button on GPIO9 for booting or reset functions. The board is ideal for IoT projects that require flexibility and small form factors.&#8221;</em></p>

<p class="wp-block-paragraph">But you may notice that the comment says that hardware I2C is on pins 5 and 6, not 8 and 9 as implied in this diagram.  It is also curious that the display is using pins that are broken out as IO too, so I&#8217;m wondering if the numbering is perhaps not accurate &#8211; or maybe there is a chip/board translation thing going on.</p>



<p class="wp-block-paragraph">Pins 5 and 6 certain work in the example code (see later).</p>



<p class="wp-block-paragraph">Note there is a very similar board that has buttons on the underside produced by 01Space.  This board has a fair bit of documentation and a schematic on GitHub, but I don&#8217;t know anything about that one.  The one I have is definitely the one shown above.</p>



<p class="wp-block-paragraph">On my travels I found this post on the Fritzing forums, which handily includes a Fritzing part for the board: <a href="https://forum.fritzing.org/t/esp32-c3-oled-0-42-mini-board-part/25830">https://forum.fritzing.org/t/esp32-c3-oled-0-42-mini-board-part/25830</a></p>



<p class="wp-block-paragraph">And most critically, this post on stackexchange which points to a review comment with some sample code to drive the display! <a href="https://electronics.stackexchange.com/questions/725871/how-to-use-onboard-0-42-inch-oled-for-esp32-c3-oled-development-board-with-micro">https://electronics.stackexchange.com/questions/725871/how-to-use-onboard-0-42-inch-oled-for-esp32-c3-oled-development-board-with-micro</a></p>



<p class="wp-block-paragraph">This appears to be saying the display should be treated as a SSD1306 display, but with only a portion of the 128&#215;64 display buffer available on screen.</p>



<p class="wp-block-paragraph">So, to get this up and running, requires the following:</p>



<ul class="wp-block-list">
<li>Install the ESP32 core for Arduino.</li>



<li>I&#8217;ve used the board type &#8220;ESP32C3 Dev Module&#8221;.</li>



<li>Install the U8g2 graphics library (<a href="https://github.com/olikraus/u8g2">https://github.com/olikraus/u8g2</a>) &#8211; this is available in the Arduino Library manager.</li>



<li>Take the code from that review comment/forum post (which I&#8217;ve reproduced below).</li>



<li>Build and upload.</li>
</ul>



<p class="wp-block-paragraph">Note &#8211; on the first upload, I have to hold BOOT whilst pressing and releasing RESET.  For subsequent uploads it seemed to be able to reset/reboot automatically as part of the Arduino upload process.</p>



<p class="wp-block-paragraph">In terms of powering the board, the simplest is using the onboard USB-C connection, but the specifications I&#8217;ve seen imply that it should be possible to connect a 3.7V to 6V source to the 5V pin and for it to survive&#8230; (I&#8217;ve not tried this).</p>



<p class="wp-block-paragraph">Other settings:</p>



<ul class="wp-block-list">
<li>If a USB serial port (e.g. for the Serial Monitor) is required, then &#8220;USB-CDC Enabled on boot&#8221; should probably be set to &#8220;Enabled&#8221;.</li>



<li>I left everything else as the defaults that came with &#8220;ESP32C3 Dev Module&#8221;.</li>
</ul>

<p class="wp-block-paragraph">The following code tests each GPIO pin in turn.  The best way to use this is with some of those &#8220;LED bars&#8221; you can get as shown below.</p>

<h3 class="wp-block-heading">Other Code/Environment Notes</h3>



<p class="wp-block-paragraph">When using &#8220;ESP32C3 Dev Module&#8221; LED_BUILTIN appears to be defined, but it doesn&#8217;t map onto the GPIO attached to the LED, which is GPIO 8.</p>



<p class="wp-block-paragraph">When no IO pins are in use the following pins appear to be pulled HIGH by default:</p>



<ul class="wp-block-list">
<li>21 &#8211; TX</li>



<li>5 &#8211; I2C to OLED</li>



<li>6 &#8211; I2C to OLED</li>



<li>8 &#8211; default I2C</li>



<li>9 &#8211; default I2C</li>
</ul>



<h4 class="wp-block-heading">Serial/USB Serial/UARTs</h4>



<p class="wp-block-paragraph">It should also be noted that in the Arduino ESP32C3 core configuration, UART0 (RX0, TX0) is configured for pins 20,21, and UART1 (RX1, TX1) is set to pins 18,19.  This means Serial will exist, and if USB CDC is enabled, will map over to the USB port.</p>



<p class="wp-block-paragraph">Update: Having found the schematic (see end of the post), actually I can see that USB is mapped onto 18,19 (indeed these are the USB D+/D- pins of the ESP32C3) which does leave 20,21 free as a non-USB hardware UART.</p>



<p class="wp-block-paragraph">So, a brief diversion into serial ports&#8230;</p>



<p class="wp-block-paragraph">From the <a href="https://github.com/espressif/arduino-esp32/blob/master/cores/esp32/HardwareSerial.h#L369">ESP32C3 definitions in the ESP32 Arduino core</a>, we can see there are various options for serial ports, specifically the underlying devices for an ESP32C3 could be any of the following:</p>



<ul class="wp-block-list">
<li>USBSerial &#8211; a native Arduino USB driver?</li>



<li>HWCDCSerial &#8211; the USB CDC driver?</li>



<li>Serial0 &#8211; the ever present default serial port, UART0 on pins 20,21.</li>



<li>Serial1 &#8211; a possible second UART, UART1 on pins 18,19.</li>
</ul>



<p class="wp-block-paragraph">To be honest I&#8217;m not entirely sure about the two USB modes, but I do know that attempting to use USBSerial does not compile, but when USB CDC on boot is enabled, then HWCDCSerial does compile fine.</p>



<p class="wp-block-paragraph">The code will always define &#8220;Serial&#8221; to something useful depending on the various hardware and compile time options, so to attempt to work out what is going on, I used the following code:</p>



<pre class="wp-block-preformatted">void setup() {<br>  Serial.begin(9600);<br>  HWCDCSerial.begin(9600);<br>  Serial0.begin(9600);<br>  //Serial1.begin(9600);<br>}<br><br>unsigned cnt;<br>void loop() {<br>  Serial.print("Serial: ");<br>  Serial.println(cnt);<br>  HWCDCSerial.print("HWCDCSerial: ");<br>  HWCDCSerial.println(cnt);<br>  Serial0.print("Serial0: ");<br>  Serial0.println(cnt);<br>  //Serial1.print("Serial1: ");<br>  //Serial1.println(cnt);<br>  delay(500);<br>  cnt++;<br>}</pre>



<p class="wp-block-paragraph">Curiously the above works fine, compiles and runs and I see an output in the serial monitor as follows:</p>



<pre class="wp-block-preformatted">Serial: 0<br>HWCDCSerial: 0<br>Serial: 1<br>HWCDCSerial: 1<br>Serial: 2<br>HWCDCSerial: 2<br>Serial: 3<br>HWCDCSerial: 3<br>Serial: 4<br>HWCDCSerial: 4<br>Serial: 5<br>HWCDCSerial: 5</pre>



<p class="wp-block-paragraph">If I include Serial1, the code will compile but my attached computer is no longer able to see a USB serial port at all.  I&#8217;m wondering if this is a bit of a bug in the interaction between the Espressif IDF and the ESP32 Arduino core:</p>



<p class="wp-block-paragraph">IDF:soc/esp32c3/include/soc/soc_caps.h declares that the ESP32C3 has two UARTs by setting:</p>



<pre class="wp-block-preformatted">#define SOC_UART_NUM                (2)<br>#define SOC_UART_HP_NUM             (2)</pre>



<p class="wp-block-paragraph">But the ESP32C3 datasheet only lists a single UART and a USB interface:</p>



<figure class="wp-block-image size-large"><a href="https://emalliab.wordpress.com/wp-content/uploads/2025/02/image-8.png"><img data-attachment-id="3078" data-permalink="https://emalliab.wordpress.com/2025/02/12/esp32-c3-0-42-oled/image-10/" data-orig-file="https://emalliab.wordpress.com/wp-content/uploads/2025/02/image-8.png" data-orig-size="1306,109" data-comments-opened="1" data-image-title="image" data-image-description="" data-image-caption="" data-large-file="https://emalliab.wordpress.com/wp-content/uploads/2025/02/image-8.png?w=663" loading="lazy" width="1024" height="85" src="https://emalliab.wordpress.com/wp-content/uploads/2025/02/image-8.png?w=1024" alt="" class="wp-image-3078" srcset="https://emalliab.wordpress.com/wp-content/uploads/2025/02/image-8.png?w=1024 1024w, https://emalliab.wordpress.com/wp-content/uploads/2025/02/image-8.png?w=150 150w, https://emalliab.wordpress.com/wp-content/uploads/2025/02/image-8.png?w=300 300w, https://emalliab.wordpress.com/wp-content/uploads/2025/02/image-8.png?w=768 768w, https://emalliab.wordpress.com/wp-content/uploads/2025/02/image-8.png 1306w" sizes="auto, (max-width: 1024px) 100vw, 1024px" /></a></figure>

<p class="wp-block-paragraph">Yet in the ESP32 Arduino core, SOC_UART_HP_NUM is used to determine if Serial1 is present or not:</p>



<pre class="wp-block-preformatted">#if SOC_UART_HP_NUM &gt; 1<br>#define RX1 (gpio_num_t)18<br>#define TX1 (gpio_num_t)19<br>#endif<br><br>extern HardwareSerial Serial0;<br>#if SOC_UART_HP_NUM &gt; 1<br>extern HardwareSerial Serial1;<br>#endif</pre>



<p class="wp-block-paragraph">If 18/19 are really a differential USB signal, then attempting to treat Serial1 as a normal serial port with RX/TX would presumably really mess up the USB link&#8230; there is no USB controller here, pins 18/19 are essentially connected directly to the USB socket.</p>



<p class="wp-block-paragraph">Note that I&#8217;m not seeing the output of Serial0 at all even though everything compiles and runs so that would match the idea that this is the hardware serial port that isn&#8217;t involved in USB.</p>



<p class="wp-block-paragraph">From all this I&#8217;m concluding that Serial0 is indeed hardware UART0 and Serial1 is hardware UART1; but that USB is connected to hardware UART1, and Serial is mapped over onto HWCDCSerial, at least when USB CDC mode is enabled on boot.</p>



<p class="wp-block-paragraph">This means that UART0 on pins 20 and 21 is available for application use without messing up USB serial printing.</p>



<h4 class="wp-block-heading">On I2C ports</h4>



<p class="wp-block-paragraph">The other thing worth noticing is that in the pins_arudino.h file for the ESP32C3 it does indeed specify that I2C is on pins 8 and 9: <a href="https://github.com/espressif/arduino-esp32/blob/master/variants/esp32c3/pins_arduino.h">https://github.com/espressif/arduino-esp32/blob/master/variants/esp32c3/pins_arduino.h</a></p>



<p class="wp-block-paragraph">However, the ESP32C3 only has a single I2C peripheral, so I&#8217;m wondering if the default build would typically put I2C pullups on pins 8 and 9, but this specific board has added additional pullups for pins 5 and 6 and routed the OLED to those instead.</p>



<p class="wp-block-paragraph">It is hard to tell from traces on the PCB as many of the connections are beneath the display, and the surface mount components are pretty small for attempting to probe the solder pads.</p>



<p class="wp-block-paragraph">Update: having found the schematic, I can see there is a different reason for pull-ups on 8 and 9; so I think we can ignore whatever the ESP32 core &#8220;thinks&#8221; the default I2C is and accept for this board it is GPIO 5 and 6.  This of course makes the above pinout diagram incorrect&#8230;</p>



<p class="wp-block-paragraph">The upshot of all this I believe is that whilst the board is pretty neat, it does mean that external I2C and SPI cannot be used as the I2C peripheral is re-routed to the display, but by using two of pins from one of the SPI peripherals (the Fast SPI &#8220;FSPI&#8221;) (these are also JTAG debugging pins, but that probably isn&#8217;t relevant right now).</p>



<p class="wp-block-paragraph">Note that the other SPI peripheral is mapped onto ESP GPIO 12-17 which is usually used to connect to the provided SPI flash memory.</p>



<h3 class="wp-block-heading">The Example OLED Code</h3>



<p class="wp-block-paragraph">So basically what is happening in this code is that it initialises a 128&#215;64 SSD1306 object within the U8g2 graphics library, but when addressing pixels on the display it always offsets the rows/columns to ensure it only uses the 72&#215;40 pixel window in the centre of the 128&#215;64 display.</p>



<p class="wp-block-paragraph">This is all set up in the width, height, xOffset, yOffset initialisation below and then xOffset and yOffset is added to the x,y coordinates for any graphics operation.</p>



<p class="wp-block-paragraph">This is the kind of thing that would be worth defining in a couple of macros or inline functions to making using the rest of the library easier.</p>



<p class="wp-block-paragraph">The constructor used is &#8220;U8G2_SSD1306_128X64_NONAME_F_HW_I2C&#8221; which is defined here: <a href="https://github.com/olikraus/u8g2/wiki/u8g2setupcpp#ssd1306-128x64_noname-1">https://github.com/olikraus/u8g2/wiki/u8g2setupcpp#ssd1306-128x64_noname-1</a> and the parameters are:</p>



<ul class="wp-block-list">
<li>U8G2_SSD1306_128X64_NONAME_F_HW_I2C (rotation, [reset [, clock, data]]) [full framebuffer, size = 1024 bytes]</li>
</ul>



<p class="wp-block-paragraph">So in this case, it is using no rotation (U8G2_R0), no RESET pin, SCL=6, SDA=5 and the default framebuffer of 1024.</p>



<pre class="wp-block-preformatted">#include &lt;U8g2lib.h&gt;<br>#include &lt;Wire.h&gt;<br><br>// there is no 72x40 constructor in u8g2 hence the 72x40 screen is<br>// mapped in the middle of the 132x64 pixel buffer of the SSD1306 controller<br>U8G2_SSD1306_128X64_NONAME_F_HW_I2C u8g2(U8G2_R0, U8X8_PIN_NONE, 6, 5);<br>int width = 72;<br>int height = 40;<br>int xOffset = 30; // = (132-w)/2<br>int yOffset = 12; // = (64-h)/2<br><br>void setup(void)<br>{<br>     delay(1000);<br>     u8g2.begin();<br>     u8g2.setContrast(255); // set contrast to maximum <br>     u8g2.setBusClock(400000); //400kHz I2C <br>     u8g2.setFont(u8g2_font_ncenB10_tr);<br>}<br><br>void loop(void)<br>{<br>    u8g2.clearBuffer(); // clear the internal memory<br>    u8g2.drawFrame(xOffset+0, yOffset+0, width, height); //draw a frame around the border<br>    u8g2.setCursor(xOffset+15, yOffset+25);<br>    u8g2.printf("%dx%d", width, height);<br>    u8g2.sendBuffer(); // transfer internal memory to the display<br>}</pre>



<h3 class="wp-block-heading">Possible Schematic</h3>



<p class="wp-block-paragraph">I&#8217;ve found a very low-resolution, possible schematic for the board and started to attempt to piece together what I could from it&#8230;</p>



<p class="wp-block-paragraph">&#8230; but then I got lucky.  Although I couldn&#8217;t access the original project page, searching for that URL in DuckDuckGo (Google was getting nowhere) eventually turned up a GitHub repository that seems related to the board, and it contained the original version of the fuzzy schematic I&#8217;d found!</p>



<p class="wp-block-paragraph">Details here: <a href="https://github.com/zhuhai-esp/ESP32-C3-ABrobot-OLED/tree/main">https://github.com/zhuhai-esp/ESP32-C3-ABrobot-OLED/tree/main</a></p>



<p class="wp-block-paragraph">But in case I lose it again, this is the schematic.</p>



<figure class="wp-block-image size-large"><a href="https://emalliab.wordpress.com/wp-content/uploads/2025/02/image-7.png"><img data-attachment-id="3065" data-permalink="https://emalliab.wordpress.com/2025/02/12/esp32-c3-0-42-oled/image-9/" data-orig-file="https://emalliab.wordpress.com/wp-content/uploads/2025/02/image-7.png" data-orig-size="1212,801" data-comments-opened="1" data-image-title="image" data-image-description="" data-image-caption="" data-large-file="https://emalliab.wordpress.com/wp-content/uploads/2025/02/image-7.png?w=663" loading="lazy" width="1024" height="676" src="https://emalliab.wordpress.com/wp-content/uploads/2025/02/image-7.png?w=1024" alt="" class="wp-image-3065" srcset="https://emalliab.wordpress.com/wp-content/uploads/2025/02/image-7.png?w=1024 1024w, https://emalliab.wordpress.com/wp-content/uploads/2025/02/image-7.png?w=150 150w, https://emalliab.wordpress.com/wp-content/uploads/2025/02/image-7.png?w=300 300w, https://emalliab.wordpress.com/wp-content/uploads/2025/02/image-7.png?w=768 768w, https://emalliab.wordpress.com/wp-content/uploads/2025/02/image-7.png 1212w" sizes="auto, (max-width: 1024px) 100vw, 1024px" /></a></figure>



<p class="wp-block-paragraph">So in this it is clear that yes, pins 5 and 6 are the I2C interface to the display and pulled HIGH.</p>



<p class="wp-block-paragraph">But we can also see that GPIO 8 is pulled HIGH via resistor R1.  But it is also connected to the LED to provide the on-board user LED via another resistor (R8).  With the reverse logic setting GPIO 8 LOW is required to illuminate the LED.</p>



<p class="wp-block-paragraph">So what about GPIO 9?  Well it isn&#8217;t immediately obvious, but if we look at the reset circuits bottom left, we can see that GPIO 9 is pulled HIGH to VCC via R6 and connected to RST2.  I&#8217;m guessing RST1 is the actual RESET button (as it connects to EN) so RST2 must be the BOOT (or &#8220;BOO&#8221; as it appears on my board) and presumably doubles as a user button too.</p>



<p class="wp-block-paragraph">Aside, we can see in the LDO section that the 5V header pin is actually VUSB which itself is connected via a 1N5819 diode to VCC5V which is the input to a ME6211C33 LDO regulator generated the 3V3 required by the system.</p>



<p class="wp-block-paragraph">My limited understanding of things would have thought that the 5V header pin would have been the other side of the diode to protect against applying 5V whilst USB is connected&#8230;but maybe I&#8217;m mis-understanding how these things work.</p>



<p class="wp-block-paragraph">But I&#8217;ve checked it with a meter, and the USB side of the diode reads 5.1V as does the pin header 5V line; whereas the regular side of the diode reads around 4.8V, as does one of the pins of the regulator, so I believe the schematic is accurate.</p>



<h3 class="wp-block-heading">Conclusion</h3>



<p class="wp-block-paragraph">Usually some perseverance with searching will find the information I need, but these little boards have been surprisingly tricky to get a handle on.  I&#8217;d just spent a while attempting to decode that fuzzy schematic, when I finally got lucky.</p>



<p class="wp-block-paragraph">Knowing that the pinout is actually incorrect, I&#8217;m now wondering about the labelling of the other pins, particularly the ADCs.  At some point I&#8217;ll check with the ESP32-C3 datasheet to be sure.</p>



<p class="wp-block-paragraph">But now I think I have plenty to be able to get on and use them.</p>



<p class="wp-block-paragraph">Those little displays are certainly pretty neat, so I can already think of a few different uses.</p>
